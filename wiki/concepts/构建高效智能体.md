# 构建高效智能体（Building Effective Agents）
## 定义
`构建高效智能体` 是一组面向落地实践的方法论原则，核心不是追求“更复杂的 agent”，而是以最小必要复杂度构建可靠、可维护、可调试的智能体系统。

## 为什么重要
很多智能体项目的问题，不在模型能力不足，而在系统设计过早复杂化。

这套方法论的重要性在于：
- 先追求正确的复杂度，而不是最大的复杂度
- 把“是否真的需要 agent”作为设计前提
- 强调工具接口、透明性和反馈回路，而不是迷信框架

## 核心判断
- 能用单次模型调用解决，就不要先上多步系统
- 能用固定工作流（workflow）解决，就不要过早升级为自主智能体（agent）
- 只有当任务开放、路径难以预定义、需要模型自主规划时，才值得引入更强自治
- AI agent 不是软件工程的银弹。它能显著降低偶然复杂度（accidental complexity），但业务边界、目标定义、验收标准和组织责任仍属于本质复杂度（essential complexity）。

## 当前理解
- `工作流（workflow）` 适合步骤稳定、边界清晰、可预测的任务。
- `智能体（agent）` 适合开放式问题、步骤数不确定、需要根据环境反馈动态调整策略的任务。
- 真正有效的智能体系统，通常可以还原为一个简单循环：
  `模型 -> 调用工具 -> 读取环境反馈 -> 判断下一步`
- 智能体质量往往取决于工具设计与环境反馈质量，而不只是底层模型能力。
- 高复杂度会带来更高成本、更长延迟，以及错误累积风险，因此必须有停止条件、检查点和人工介入机制。
- 早期 LLM agent 常被拆成三大组件：规划（planning）、记忆（memory）和工具使用（tool use）。后来的 harness 工程不是推翻这三件事，而是在它们外面补上 workflow、评估、权限、持久状态和治理。
- 多想一会儿是一种资源，而不是免费能力。[[wiki/concepts/测试时计算|测试时计算（test-time compute）]] 对中等难度任务很有价值，但不能替代强模型、好工具和真实反馈。

## 基础结构
Lilian Weng 的 2023 年综述给出了一个很稳定的 agent 基础结构：
- 规划（planning）：把复杂任务拆成子目标，并通过反思修正行动
- 记忆（memory）：用上下文窗口承载短期记忆，用外部存储承载长期记忆
- 工具使用（tool use）：通过 API、代码执行、检索、专业工具连接模型权重之外的世界

这套结构今天仍然有用，但需要补充一个工程判断：planning、memory、tool use 本身不是完整系统。真正上线时还需要 harness 来管理它们如何循环、如何停下、如何被评估、如何被审计、如何处理权限。

可以把演进压缩成：
- 早期 agent：`LLM + planning + memory + tools`
- 工程化 agent：`LLM + tools + context + workflow + eval + permissions + state`
- 自我改进型 agent：进一步把 context、workflow、harness code 变成可评估、可治理的优化对象

## 设计原则
### 1. 从简单开始
- 先尝试提示词优化、检索增强、少样本示例等轻量方案
- 只有当简单方法效果不足时，才增加多步结构
- 每次增加复杂度都应有明确收益，而不是“感觉更高级”

### 2. 区分工作流与智能体
- 工作流由代码定义路径，稳定但灵活性较低
- 智能体由模型决定路径，灵活但更难控制
- 设计时应先问：这个任务到底需要“编排”，还是需要“自主决策”？

### 3. 保持透明性
- 尽量显式展示计划、执行状态和关键判断
- 让系统容易调试，而不是把行为埋进黑盒框架
- 重要节点应支持人工确认或人工接管

### 4. 重视工具设计
- 工具的输入输出应清晰、稳定、容易理解
- 参数名、文档和边界条件要为模型使用而设计
- 好工具会降低模型犯错概率，差工具会放大系统不稳定性

### 5. 依赖环境反馈，而不是自我幻想
- 智能体每一步都应尽量从环境拿到“真实反馈”
- 例如工具返回结果、代码执行结果、页面状态、数据库响应
- 没有反馈的长链推理更容易偏航

### 6. 设置边界与护栏
- 设定最大轮数、停止条件、失败退出策略
- 在高风险操作前增加确认点
- 在可控环境中充分测试，再逐步扩大自治范围

### 7. 控制 thinking budget
- 不要让所有任务都默认走长 CoT 或多轮 loop
- 根据任务难度、风险和可验证性决定思考预算
- 如果任务超出模型能力，继续循环通常只会消耗成本并放大幻觉，应升级工具、模型或人工介入

## 适用场景
- 编码代理：多文件修改、调试、验证、迭代修复
- 客服或运营代理：既需要对话，也需要执行动作
- 开放式研究任务：多轮检索、筛选、比较与综合
- 需要根据实时环境结果调整路径的自动化任务

## 不适合的场景
- 单轮问答就足够的任务
- 规则清晰、流程固定的标准操作
- 对延迟和成本极其敏感的场景
- 一旦出错就代价很高、又缺少人工复核机制的任务

## 与现有知识库的关系
- 它的一个底层前提是 [[wiki/concepts/上下文工程|上下文工程（context engineering）]]：如果模型每轮看到的信息质量不高，再好的方法论也难稳定落地。
- 它细化了智能体系统（agent systems）的工程落地层。
- 它也能作为后续阅读 agent 产品、论文和案例时的评价标尺。
- 它和 [[wiki/concepts/软件工程|软件工程]] 形成互补：前者讲 agent 如何以最小必要复杂度落地，后者提醒我们不要把任何单一技术当作绕过本质复杂度的魔法。
