# 分布式存储系统

## 定义
分布式存储系统把数据和处理分散到多台机器、多个故障域乃至多个地域，同时对外提供可扩展、可用、可恢复的数据服务。它的难点不只是“把数据切开”，还包括一致性、定位、迁移、后台维护、故障恢复、资源隔离和长期运维。

[[wiki/entities/Bigtable|Bigtable]] 的二十年演化提供了一个有代表性的案例：核心数据模型和服务路径长期稳定，但系统围绕复制、分析、控制面、可靠性和成本治理不断扩展。

## 基础结构
以 Bigtable 为例，一套可扩展存储系统通常包含：
- **数据模型**：明确排序键、分片边界、事务边界和 schema 灵活性。
- **数据面**：客户端直接访问承载分片的 server，处理在线读写。
- **控制面**：负责分片位置、调度、负载均衡、schema 和元数据。
- **持久化层**：用 WAL 保证写入恢复，用内存结构和不可变文件组织数据。
- **后台维护**：compaction、GC、备份、校验、复制和冷热迁移。
- **观测与运维**：探针、SLI/SLO、告警、容量管理和故障处置。

## 可迁移的架构原则

### 1. 稳定内核，扩展外围
长寿系统的演化不一定依靠周期性重写。更稳健的路线是守住简单、明确的核心抽象，让新功能复用现有日志、文件格式、时钟、水位线和调度机制。

这要求架构最初就留有扩展点，也要求每次新增能力都回答：它是否改变前台读写路径、事务边界或故障模型？

### 2. 把可延迟工作移出前台路径
复制、物化视图、compaction、备份和完整性验证都可以异步完成，以保护在线延迟。但异步化会产生新的状态问题：
- 处理到哪里
- 哪些事件已经交付
- 乱序和重复如何处理
- split/merge 后状态如何转移
- 哪些历史数据可以安全回收

因此，watermark、sequencer、continuation token 和持久化进度不是实现细节，而是异步系统的核心数据模型。

### 3. 控制面必须独立扩展
当数据量和分片数上升时，最先变慢的未必是读写，而可能是 metadata、location lookup、master 锁、schema 更新、GC 和 rebalancer。

常见策略包括：
- 缩小全局串行区，改用细粒度锁和并行任务。
- master 只协调，把昂贵工作下放到 worker 或 data server。
- 给 metadata 独立资源域，并为 location lookup 增加缓存、hint 或 proxy。
- 把任务进度持久化，使后台工作可恢复、可重试。

### 4. 隔离优先于统一堆资源
在线点查、批量扫描、compaction、复制和导入的资源形态不同。把所有任务放在同一批 server 上，会让平均利用率看起来更高，却使尾延迟和故障耦合变差。

更有效的做法是用 partition、priority、独立 worker 和便宜资源层隔离负载，并让每类资源单独伸缩。

### 5. 可靠性要端到端验证
在超大规模下，极小概率的硬件或软件错误也会成为日常事件。可靠性不能只依赖单点 checksum，而应贯穿：
- 客户端生成与验证
- 网络与 RPC 边界
- 日志、内存结构和持久化文件
- 复制与 compaction
- 文件安装前读回
- 线上持续巡检

“多做一次完整验证”的资源成本，常常低于静默损坏进入长期数据后的恢复成本。

### 6. 资源效率是架构目标
资源效率不只是压缩机器数，可以分成三条路径：
- 减少 headroom：自动伸缩与快速 slack pool。
- 减少单位工作用量：更好的 cache、filter、调度和 compaction。
- 资源分层：让批处理、离线读、文件构建使用更便宜的计算和存储。

缓存也不应追求“越大越好”，而应在 RAM 成本与 cache miss 带来的 CPU/I/O 成本之间动态寻找 TCO 拐点。

## 数据模型与应用责任
分布式存储提供的事务和一致性边界，会直接塑造应用设计。Bigtable 的单行事务鼓励把需要原子更新的数据放在同一行，但过大的行又会带来性能问题；最终一致复制减少协调成本，却要求应用处理陈旧读取和跨副本会话一致性。

因此，选型时不能只比较峰值吞吐，还要问：
- 业务不变量能否落在系统的事务边界内？
- 热点是否能通过 row key 自然分散？
- 应用能否正确处理重试、重复、乱序和延迟？
- 团队是否具备长期运行这种系统的专业能力？

## 运维模型也是系统设计
Bigtable 从“各团队自己运行”转向专门 SRE 团队提供公司级服务，说明运维知识的组织方式会反过来影响系统质量。

可复用原则是：
- 用平台默认值固化安全基线，例如默认备份。
- 标准化资源规格，换取可预测性能与简化容量规划。
- 同时运行内部 metadata prober 和外部 black-box prober。
- 将常见故障处理与容量策略集中到拥有领域知识的团队。

## 与其他概念的关系
- 和 [[wiki/concepts/软件工程|软件工程]]：可变性是软件的本质属性；稳定架构的价值在于允许系统增量生长，而不是拒绝变化。
- 和 [[wiki/syntheses/企业数仓 Text-to-SQL Agent 落地规划|企业数仓 Text-to-SQL Agent 落地规划]]：数据库一致性、方言、schema、负载隔离和验证边界都会成为 agent 的真实环境约束。
- 和 [[wiki/concepts/AI评估|AI评估]]：分布式系统的探针、SLI/SLO 和端到端验证体现了“外部可观测证据优先于内部自信”。

## 开放问题
- 在稳定内核上不断增加 SQL 与计算能力，何时会跨过“可扩展架构”与“职责膨胀”的边界？
- 强一致系统和最终一致系统的总成本，应该如何把应用补偿逻辑、运维难度和故障恢复一起计入？
- 控制面外置和资源分层提升了隔离性，但如何控制由此增加的组件数量与诊断路径？
