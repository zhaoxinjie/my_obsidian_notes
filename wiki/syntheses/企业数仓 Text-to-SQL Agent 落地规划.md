# 企业数仓 Text-to-SQL Agent 落地规划
## 目标
这份规划面向一个更真实的企业数仓 `text-to-SQL agent` 场景。目标不是做一个“能生成 SQL 的 demo”，而是逐步建设一个：
- 能找对表和字段
- 能理解业务口径
- 能根据方言与执行反馈持续修正
- 能被稳定评估与持续迭代

的数仓分析系统。

## 先校准问题定义
最重要的第一步，是把问题从 `NL -> SQL` 改写成：

`业务问题 -> 语义理解 -> 检索元数据/文档 -> 规划查询路径 -> 生成与执行 -> 根据反馈修正 -> 返回结果`

如果团队仍然把它只看成“生成 SQL”，后面的系统设计大概率会不完整。

## 推荐的分阶段路线
### 阶段 1：打基础（2-4 周）
这一阶段的目标不是追求高分，而是把后面一切能力依赖的基础打稳。

#### 1. 统一核心指标与维度
- 先挑 `10-20` 个核心指标域。
- 明确口径、维度、时间粒度、过滤规则、默认 join。

#### 2. 补核心表元数据
- 先不追全仓。
- 只补最关键的 `20-50` 张表。
- 每张表至少补：用途、字段说明、负责人、更新时间、常见查询模式。

#### 3. 整理业务词典
- 建立业务别名、缩写、口语表达到正式语义层的映射。
- 特别关注内部黑话和跨团队不同叫法。

#### 4. 整理方言知识
- 把常用数据库方言坑单独整理成知识包。
- 至少先覆盖：日期、时间、字符串、数组/json、窗口函数、NULL 语义。

#### 5. 建最小 eval 集
- 收集 `20-50` 个真实任务。
- 每题至少有参考答案、失败类型、相关表、正确口径。

### 阶段 2：做最小 agent（4-8 周）
这一阶段的目标是做一个真正可试跑的最小闭环（minimum viable loop）。

#### 1. 系统拆成 4 段
- 意图理解（intent understanding）
- 检索（metadata / docs / examples retrieval）
- 生成（SQL generation / planning）
- 执行与修正（execution and repair）

#### 2. 不要一开始全自动
- 第一版允许更多显式中间步骤。
- 比如先返回候选表，再生成 SQL，再试跑。
- 这样更容易 debug。

#### 3. 建执行反馈闭环
- 必须能试跑 SQL。
- 必须能把报错回传给模型。
- 必须记录每次修正轨迹。

#### 4. 记录 transcript
- 保留每次检索、生成、执行、修正的轨迹。
- 后续很多能力提升都靠读失败 transcript，而不是只看最终分数。

### 阶段 3：把系统做稳（6-12 周）
这一阶段的目标是从“偶尔能用”走向“可以稳定迭代”。

#### 1. 区分 capability eval 与 regression eval
- capability：看天花板
- regression：守住底线

#### 2. 建错误分类 dashboard
- 每周看错误分布，而不是只看总成功率。
- 比如：
  - schema linking 错
  - 口径错
  - 方言错
  - 执行修复失败
  - 最终业务理解错

#### 3. 建最小 observability
- 记录成功率、重试次数、平均轮数、平均成本、失败原因。
- 否则后面很难判断到底是模型退化还是数据变了。

#### 4. 做人工 review 机制
- 对高价值任务保留人工抽样 review。
- 不要过早完全相信自动评估。

## 系统架构建议
### 1. 不要直接把全 schema 塞进上下文
- 先检索最相关的 schema 子集。
- 必要时二次检索字段级说明和样例查询。

### 2. 引入轻量语义层
- 语义层不是锦上添花，而是企业数仓场景里的必要约束。
- 它能显著降低“SQL 对但业务错”。

### 3. 工具至少要有这几类
- schema / metadata 检索
- 文档检索
- SQL 执行
- 错误回传
- 历史查询样例检索

### 4. 慎重处理代码库与 dbt 上下文
- 如果你们依赖 dbt、YAML、模型定义、指标层代码，那么这部分是高价值上下文。
- 但不要全量灌入，要按任务按需读取。

## 评估建议
### 1. 不只看 execution accuracy
至少同时看：
- 检索是否命中
- SQL 是否可执行
- 结果是否业务正确
- 修错能力是否稳定

### 2. 不只测单轮
真实企业任务经常需要多轮修正。
- 所以要测一轮成功率
- 也要测允许修错后的最终完成率

### 3. 不只测最终答案
如果最终答案对了，但中间绕了很多错路，成本和稳定性可能仍然不可接受。

建议记录：
- 轮数
- token / 成本
- 重试次数
- 是否查对文档
- 是否命中错误类型

## 我更推荐的组织方式
### 现在就做
- 统一核心口径
- 补核心元数据
- 整理别名词典
- 建最小 eval 集
- 搭执行反馈闭环

### 一个月内做
- 搭 transcript 存档
- 做错误分类 dashboard
- 区分 capability / regression eval
- 引入轻量语义层

### 后面再做
- 更复杂的多步 planner
- 更自动化的修错策略
- 跨库协同查询
- 更完整的生产 A/B 测试

## 风险提醒
最容易踩的坑通常不是“模型不够强”，而是：
- 口径没统一
- 元数据太差
- 任务集不真实
- 只看最终 SQL
- 没有执行反馈
- 没有 transcript 复盘

如果这些问题不先解决，后面无论换模型、调 prompt、加 agent，都会反复撞墙。

## 一句话建议
先把系统建成一个“会查口径、会找表、会试跑、会修错、能被稳定评估”的最小闭环，再去追求更强的自动化和更高的 benchmark 分数。
